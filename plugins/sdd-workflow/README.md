# SDD Workflow

[![License: MIT](https://img.shields.io/badge/license-MIT-green)](./LICENSE)
[![Platform](https://img.shields.io/badge/platform-macOS%20%7C%20Linux-lightgrey)]()

A unified Claude Code plugin supporting AI-driven Specification-Driven Development (AI-SDD) workflow with multi-language
support.

[日本語版 README](README.ja.md)

## Overview

This plugin provides tools to prevent Vibe Coding problems and achieve high-quality implementations using specifications
as the source of truth. Supports multiple languages via `SDD_LANG` configuration.

## Supported Environments

| Requirement | Version | Notes                                  |
|:------------|:-------:|:---------------------------------------|
| macOS       |    ✅    | Fully supported                        |
| Linux       |    ✅    | Fully supported                        |
| Windows     |    ❌    | Not supported (see alternatives below) |
| Python      |  3.7+   | Required for hook scripts              |
| Claude Code | 2.1.199+ | Required for named skill arguments (`arguments` frontmatter / `$name` substitution). On older versions, `$name` placeholders are not substituted and skills fall back to interpreting the raw argument string |

### Windows Limitations

This plugin's hooks execute `python3` via bash and do not work on native Windows environments.

### Alternatives for Windows Users

1. **Use WSL (Windows Subsystem for Linux)** (Recommended)
    - Install WSL2 and run Claude Code within the Linux environment
    - [WSL Installation Guide](https://learn.microsoft.com/en-us/windows/wsl/install)

2. **Use Git Bash**
    - Git Bash included with Git for Windows may allow execution
    - [Git for Windows](https://gitforwindows.org/)

### What is Vibe Coding?

Vibe Coding occurs when AI must guess thousands of undefined requirements due to vague instructions.
This plugin solves this problem by providing a specification-centered development flow.

## Quick Start

### 1. Project Initialization

**For projects using this plugin for the first time, run `/sdd-init`.**

```
/sdd-init
```

This command automatically:

- Adds the AI-SDD Instructions section to your project's `CLAUDE.md`
- Creates the `.sdd/` root directory. The `requirement/`, `specification/`, `adr/`, and `task/`
  subdirectories are **not** created up front — each appears automatically when the first file is written
  into it
- Generates the PRD, specification, design document, and decision log (ADR) template files
- Adds `.sdd/.cache/` (or `${SDD_ROOT}/.cache/` for a custom root) to your project's `.gitignore`, since that
  directory is a generated artifact. Existing lines are never rewritten — the entry is appended once, or the
  file is created with just that entry if you have none. Re-running adds nothing further, and only `.cache/`
  is ignored: your documents under `.sdd/` stay tracked

Re-running `/sdd-init` is safe at any time: an existing template file is skipped rather than overwritten, and
the `.gitignore` entry is not duplicated.

`CONSTITUTION.md` is **not** generated by `/sdd-init`. Run `/constitution init` to create one, so it can be
customized to your project instead of copied from a generic template.

## Usage

### Ticket Numbers

Since v5.0.0 the technical design draft and the task log live under `task/{ticket-number}/`, so several
skills need a ticket number. How it is passed differs per skill:

| Skill                                        | How the ticket is passed                   | Required                                                           |
|:---------------------------------------------|:-------------------------------------------|:-------------------------------------------------------------------|
| `/generate-spec`                             | Option only                                | Yes — resolved interactively when omitted; required in `--ci` mode  |
| `/plan-refactor`                             | Option only                                | Yes — resolved interactively when omitted; required in `--ci` mode  |
| `/task-breakdown`                            | Second positional argument, or option       | Yes — no fallback                                                   |
| `/implement`, `/checklist`, `/run-checklist` | Second positional argument, or option       | No — the feature name is used as the task directory when omitted    |
| `/clarify`                                   | Second positional argument, or option       | No — the PRD, the spec and any v4.x design document are analyzed when omitted |
| `/task-cleanup`                              | First positional argument, or option        | No — the whole `task/` directory is targeted when omitted           |
| `/check-spec`                                | Option only                                 | No — scopes the auxiliary design draft; see "Consistency Check"     |
| `/render-adr-review`                         | Second positional argument, or option       | No — names the output file; the source file's feature name is used when omitted |

Wherever the ticket is passed as an option, **both `--ticket <number>` (space) and `--ticket=<number>`
(equals sign) are accepted** and mean the same thing. For the skills that also take it positionally, the flag
form does not consume the positional slot, so `/task-breakdown user-auth --ticket=123` still resolves the
feature name to `user-auth`.

#### If You Don't Use a Ticket Tracker

The ticket number is used only as a **directory name** under `task/` and as the value of the `ticket` front
matter field. Nothing validates it against GitHub, JIRA, or any other tracker, so any stable identifier
works:

```
/generate-spec User authentication feature --ticket user-auth
/task-breakdown user-auth user-auth
/implement user-auth
```

Passing the **feature name** as the ticket is the simplest convention: `/implement`, `/checklist`, and
`/run-checklist` already default to it, so all of a feature's `task/` files end up in one directory. A branch
name or a date-prefixed slug (`2026-09-10-user-auth`) works equally well.

The only step that needs a real tracker is `/task-cleanup`'s completion comment. When no tracker can be
determined, that step is skipped and reported instead of failing, and the ticket-to-feature link survives in
the `ticket` field of `adr/{feature-name}.md`.

### Command Usage Examples

#### PRD Generation

```
/generate-prd A feature for users to manage tasks.
Available only to logged-in users.
```

#### Specification/Design Document Generation

```
/generate-spec User authentication feature. Supports login and logout with email and password.
```

#### Consistency Check

```
/check-spec user-auth
/check-spec user-auth --ticket TICKET-123   # scope the auxiliary design draft to one ticket
/check-spec user-auth --ticket=TICKET-123   # same thing
/check-spec user-auth --full                # also review PRD <-> spec <-> adr and quality
```

`--ticket` decides **which** `task/{ticket-number}/design-draft.md` is read as auxiliary input. When it is
omitted, the helper script still picks a draft on its own where the choice is unambiguous, and gives up
rather than mixing another ticket's design into the check:

| Situation                                                                       | What is read                           |
|:--------------------------------------------------------------------------------|:---------------------------------------|
| No draft exists (the normal state after implementation)                         | Nothing; no design check is reported    |
| `--ticket <number>` given                                                       | Only that ticket's draft                |
| A draft's front matter `depends-on` references a target spec's ID (`spec-*`)     | That draft, even with others in flight  |
| Exactly one draft exists project-wide                                           | That draft                              |
| Several drafts exist and none could be tied to this run                         | **None** — the run reports which ones it skipped so you can re-run with `--ticket` |

So `--ticket` is only strictly needed for the last row. Adding `depends-on: ["spec-{feature}"]` to each
draft's front matter avoids it too.

`--full` additionally invokes the `spec-reviewer` agent for a **document-level** review: PRD ↔ spec
traceability, spec ↔ adr decision consistency (the current — latest, non-superseded — decisions agree with
the spec, the spec does not rely on a superseded decision, and spec-driving decisions are recorded at all),
CONSTITUTION.md compliance, section completeness, vague-description detection, and SysML requirement ID
validity. A feature with no decision log yet is reported as **not applicable**, which is neither a finding
nor "consistent". `adr/` is append-only, so a fix lands either in the spec or in a newly appended entry with
a `Supersedes` item — never by editing an existing entry.

### Complete Workflow Example

Here's a complete workflow for implementing a new "User Authentication" feature.

#### Step 1: Project Initialization (First Time Only)

```
/sdd-init
```

Creates the `.sdd/` root and the document templates. Run `/constitution init` afterwards to generate the
project constitution (`CONSTITUTION.md`) — `/sdd-init` does not create it.

#### Step 2: Create Requirements Document (PRD)

```
/generate-prd User authentication feature. Login and logout with email and password.
Includes session management and password reset functionality.
```

→ `.sdd/requirement/user-auth.md` is generated.

#### Step 3: Generate Specification and Design Documents

```
/generate-spec user-auth --ticket TICKET-123
```

→ `.sdd/specification/user-auth_spec.md` is generated, along with a temporary design draft at
`.sdd/task/TICKET-123/design-draft.md`.

#### Step 4: Clarify Specifications

```
/clarify user-auth
```

Scans specifications across 9 categories and generates questions for unclear points. Answers are automatically
integrated into specs.

#### Step 5: Task Breakdown

```
/task-breakdown user-auth TICKET-123
```

→ `.sdd/task/TICKET-123/tasks.md` is generated with the task list.

#### Step 6: Generate Quality Checklist

```
/checklist user-auth TICKET-123
```

→ `.sdd/task/TICKET-123/checklist.md` is generated with 9-category quality checklist.

#### Step 7: TDD-based Implementation

```
/implement user-auth TICKET-123
```

Proceeds through 5 phases (Setup→Tests→Core→Integration→Polish) with automatic progress marking.

#### Step 8: Verify Checklist Items

```
/run-checklist user-auth TICKET-123
```

Automatically runs tests, linters, and security scans to verify checklist items. Generates verification report.

#### Step 9: Consistency Check

```
/check-spec user-auth
```

Verifies consistency between implementation and specifications, reporting any discrepancies.

#### Step 10: Task Cleanup

```
/task-cleanup TICKET-123
```

Cleans up temporary files under `task/` (including `design-draft.md`) and integrates important design
decisions into `adr/{feature-name}.md` (append-only) before deletion.

## Migration from v4.x

### Breaking Changes in v5.0.0

1. **`specification/{feature-name}_design.md` is no longer a persistent document.** Technical Design
   Documents now start as a temporary draft at `task/{ticket-number}/design-draft.md` and are deleted
   after implementation, like the rest of `task/`
2. **New `adr/` directory.** Only the decisions, their rationale, and rejected alternatives are
   persisted, in `adr/{feature-name}.md` (append-only)
3. **`/generate-spec` now requires a ticket number.** The design draft path is ticket-scoped
   (`--ticket <number>` or `--ticket=<number>`, or resolved interactively), since the draft lives under
   `task/{ticket-number}/` instead of `specification/`
4. **`/check-spec` now compares the implementation against the spec, not against a design document.**
   The spec under `specification/` is the first-class baseline; a design draft is used only as an
   optional auxiliary input for what a spec cannot express (module structure, technology stack). A
   missing draft is the normal state after implementation and is never reported as a discrepancy
5. **`/plan-refactor` decides Case A / Case B from the spec, and writes the plan into the design
   draft.** The case used to be decided by the presence of `specification/{feature-name}_design.md`;
   it now comes from whether a **spec** exists (matched with *and* without the `_spec` suffix). The
   refactoring plan goes to `task/{ticket-number}/design-draft.md`, while a reverse-engineered spec is
   still persisted under `specification/`
6. **`/plan-refactor` now takes a ticket number** (`--ticket <number>` or `--ticket=<number>`, or
   resolved interactively; required in `--ci` mode), because the design draft path is ticket-scoped
7. **`/task-breakdown` now requires a ticket number.** Both the design draft it reads and the
   `tasks.md` it writes live under `task/{ticket-number}/`. `tasks.md` is always written to
   `task/{ticket-number}/tasks.md` — the previous fallback to `task/{feature}/tasks.md` is gone
8. **`doc-consistency-checker` now checks PRD ↔ spec ↔ adr**, not PRD ↔ spec ↔ design

### Extracting Existing `*_design.md` Files into `adr/`

If your project has persisted `specification/{feature-name}_design.md` files created before this change,
extract their decision history into `adr/{feature-name}.md`.

**This migration is not urgent.** Existing `specification/*_design.md` files **remain valid**: the naming
hook accepts them, and the skills that read a technical design read them as **supplementary input** (their
absence is equally normal). Nothing reports them as a violation or asks you to remove them.
Just don't create new ones — new technical design goes to `task/{ticket-number}/design-draft.md`.

When such files are present, the `session-start` hook writes `.sdd/MIGRATION_PENDING.md` listing them (the
first 10 by path, plus a count of the rest) and pointing back at this section. The list is **independent of
`.sdd/UPDATE_REQUIRED.md`**, which only ever reports a stale `CLAUDE.md`: running `/sdd-init` deletes
`UPDATE_REQUIRED.md` but leaves `MIGRATION_PENDING.md` in place. It is rewritten at every session start for
as long as at least one such file exists, and deleted automatically once none are left — so you can work
through them at your own pace without the list going missing. It is a generated file; edits to it do not
survive the next session.

1. If you use a custom `directories.adr` name in `.sdd-config.json`, set it before migrating (it defaults
   to `adr`). Then re-run `/sdd-init` to get `ADR_TEMPLATE.md`, which documents the append-only entry
   format — re-running is safe at any time, since existing files are never overwritten. Note that
   `/sdd-init` does **not** create the `adr/` directory itself: like `requirement/`, `specification/`, and
   `task/`, it appears when the first file is written into it
2. **Locate the design decisions** in each `*_design.md` — the section(s) explaining why a technology,
   architecture, or approach was chosen
3. **Create `adr/{feature-name}.md`**, mirroring the feature's path under `specification/`
   (e.g. `specification/auth/user-login_design.md` → `adr/auth/user-login.md`), with the front
   matter fields defined for `type: "adr"` in `shared/references/front_matter_reference.md`
   (`id`, `type`, `title`, `status`, `created`, `updated`, `sdd-phase`, `depends-on`, and `ticket` if
   known). `status` is `"approved"` — decisions are recorded after the fact. Leave the front matter
   `supersedes`/`superseded-by` fields out: they retire a decision-log **file** as a whole (renamed,
   split, or merged feature), not one entry reversing another
4. **Append one entry per decision** as a `##` block at the end of the file, using the fixed entry
   format:
   - Heading `## YYYY-MM-DD {decision title}` — the date the decision was made
   - `- **Decision**:` what was decided
   - `- **Rationale**:` why, including the constraint that forced it
   - `- **Rejected alternatives**:` each alternative and why it lost, or `None considered` when there
     were none (never invent one)
   - `- **Supersedes**:` only when this entry reverses an earlier entry **in the same file** — a link to
     that entry's heading plus one line on what changed. The superseded entry is never edited; `adr/` is
     append-only
5. **Do not carry over** implementation steps, technology stack listings without rationale, or content
   already reflected in the current codebase — only the *why*, not the *how* or *what*
6. **If you delete the old `*_design.md`** once its decisions are captured in `adr/`, find the leftover
   references yourself first. Neither `/check-spec` nor `doc-consistency-checker` verifies Markdown link
   health, so a dangling reference will **not** be reported for you. Two searches are needed, because
   in-body links hold the **path** while `depends-on` front matter holds the document's **`id`** — the
   same file is never named the same way in both:

   ```bash
   # 1. Path references: in-body links, prose, and code fences
   grep -rn "_design\.md" .sdd/ --exclude-dir=.cache --exclude=AI-SDD-PRINCIPLES.md

   # 2. ID references: `depends-on` entries, and the doc's own `id`
   #    Flat: design-{feature-name}   Hierarchical: design-{parent-feature}-{feature-name}
   grep -rn "design-user-auth" .sdd/ --exclude-dir=.cache --exclude=AI-SDD-PRINCIPLES.md
   ```

   Replace `.sdd` with your `root` if you customized it, and `user-auth` with the feature you are
   migrating. Both exclusions matter: `.sdd/.cache/` is regenerated at every session start, and
   `.sdd/AI-SDD-PRINCIPLES.md` is overwritten by the `session-start` hook from the installed plugin —
   editing either is pointless, and their hits are the plugin's own explanatory text, not references to
   your document.

   Of the remaining hits, update the ones that point at the file you deleted: in-body links become links
   to `adr/{feature-name}.md`, and a `depends-on` entry becomes either that ADR's `id`
   (`adr-{feature-name}`) or the current draft's `id` (`design-{ticket-number}`), depending on which the
   dependency actually meant. Drop the reference if it no longer means anything. Hits that merely mention
   the `*_design.md` convention in prose are not references and need nothing. Keeping the old file in
   place is also a valid outcome (see the note above), in which case neither search needs acting on

Use `/render-adr-review adr/{feature-name}.md` to read the finished log back, structured by decision /
rationale / rejected alternatives.

See `AI-SDD-PRINCIPLES.md` § "Architecture Decision Record" for the full `adr/` field and format
reference.

## Known Limitations

- **`adr/` drift against the implementation is not detected automatically.** `/check-spec` compares the
  implementation with the abstract spec, and `--full` adds document-level `PRD ↔ spec ↔ adr` review — no
  check reads an `adr/` entry and verifies the code still matches it. Review the decision log by hand
  (`/render-adr-review adr/{feature-name}.md` helps) when an implementation changes a recorded decision, and
  record the reversal as a **new** entry with a `Supersedes` item rather than editing the old one.
- **Markdown link health is not verified.** Neither `/check-spec` nor `doc-consistency-checker` reports
  dangling links, so after deleting or renaming a document, find the leftover references yourself (see the
  `grep` in "Extracting Existing `*_design.md` Files into `adr/`").

## Tool Permissions

Every skill in this plugin declares `allowed-tools` in its front matter. That field is a **pre-approval of tool
permissions** — the tool calls a skill may make without asking you. It is *not* a restriction: every tool stays
callable, and anything that is not pre-approved simply falls back to the normal confirmation prompt.

This plugin keeps that pre-approval deliberately narrow: no skill pre-approves bare `Bash`, so none of them can run an
arbitrary shell command without asking, and writes are pre-approved only inside your documents and a fixed set of setup
files.

| Operation                                                               | Pre-approved scope                                                          | Behavior                        |
|:------------------------------------------------------------------------|:----------------------------------------------------------------------------|:--------------------------------|
| AI-SDD document writes                                                  | `Edit(.sdd/**)`                                                             | Applied without a prompt        |
| Setup files for `/sdd-init`, `/constitution`, `/recommend-front-matter` | `Edit(CLAUDE.md)`, `Edit(.sdd-config.json)`, `Edit(.claude/rules/**)`       | Applied without a prompt        |
| Bundled helper scripts (one fixed path per script, see the caveat below) | `Bash(python3 "${CLAUDE_PLUGIN_ROOT}/skills/<name>/scripts/<script>.py" *)` | Applied without a prompt        |
| Everything else                                                         | Not pre-approved                                                            | Claude Code asks you to confirm |

"Everything else" covers writes outside the paths above, arbitrary shell commands, the delete commands `git rm` / `rm`,
and any test or linter invoked directly. `/implement` and `/task-cleanup` pre-approve **no** `Bash` at all, so you are
asked before each command they run — including `/task-cleanup`'s `git ls-files` and its `git rm` / `rm` deletions.

### A Pre-Approved Script That Runs Your Project's Commands

The "bundled helper scripts" row deserves a closer look, because one of those scripts is not self-contained.
`/run-checklist` pre-approves

```
Bash(python3 "${CLAUDE_PLUGIN_ROOT}/skills/run-checklist/scripts/run-verification.py" *)
```

and that script executes **your project's own test, lint, type-check, and audit commands** itself via `subprocess`,
without a further prompt. It detects the project type from a manifest file (`package.json`, `pyproject.toml`,
`Cargo.toml`, `go.mod`, `setup.py`, `requirements.txt`, `Gemfile`, or — with no manifest at all — a `tests/` or
`test/` directory containing `test_*.py` / `*_test.py`) and then runs the first available command from a fixed table:

| Project type | Commands it may run                                                                      |
|:-------------|:-----------------------------------------------------------------------------------------|
| Node         | `npm test`, `npx eslint .` / `eslint .`, `npx tsc --noEmit` / `tsc --noEmit`, `npm audit` |
| Python       | `pytest`, `ruff check .`, `mypy .`, `pip-audit` / `safety check`                          |
| Rust         | `cargo test`, `cargo clippy`, `cargo audit`                                               |
| Go           | `go test ./...`, `golangci-lint run`, `govulncheck ./...`                                 |
| Ruby         | `bundle exec rspec`, `bundle exec rubocop`, `bundle exec bundler-audit`                   |

Approving the wrapper once therefore lets those commands run for that invocation. Two limits keep it bounded: the table
above is the *only* source of commands — a verification command written inside a `checklist.md` item is never executed,
only recorded as a manual instruction, because `allowed-tools` grants the script and not bare `Bash` — and each command
is killed after 300 seconds.

If you would rather confirm each command, don't run `/run-checklist` — run your test, lint, and audit commands yourself
and tick the items in `task/{ticket-number}/checklist.md` by hand.

Of the ten bundled helper scripts (`find-spec-docs.py`, `validate-files.py`, `prepare-prd.py`, `prepare-spec.py`,
`find-implementation-files.py`, `scan-existing-docs.py`, `scan-documents.py`, `run-verification.py`,
`init-structure.py`, `update-claude-md.py`), `run-verification.py` is the only one that starts another process.

### Reducing Confirmation Prompts

If you would rather not be asked, grant the permissions yourself in your project's `.claude/settings.json` (or your user
`~/.claude/settings.json`):

```json
{
  "permissions": {
    "allow": [
      "Edit(.sdd/**)",
      "Bash(npm test:*)",
      "Bash(git ls-files:*)",
      "Bash(git rm:*)",
      "Bash(rm:*)"
    ]
  }
}
```

The last three cover `/task-cleanup`'s step 9, which checks tracking with `git ls-files` and then deletes with `git rm`
(tracked paths) or `rm` (untracked ones). `Bash(rm:*)` allows *any* `rm`, so add it only if that is acceptable to you.

**Use `Edit(<path>)`, not `Write(<path>)`.** `Write(<path>)` is not matched by file permission checks; an
`Edit(<path>)` rule covers *all* file-editing tools, including Write.

### Custom SDD Root

If `.sdd-config.json` sets `root` to something other than `.sdd`, the plugin's `Edit(.sdd/**)` pre-approval no longer
matches your documents, so document writes fall back to a confirmation prompt. `allowed-tools` cannot reference
`${SDD_ROOT}` (only `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, and `${CLAUDE_PROJECT_DIR}` are expanded there), so
add a rule for your own root to `.claude/settings.json`:

```json
{
  "permissions": {
    "allow": [
      "Edit(docs/sdd/**)"
    ]
  }
}
```

## Serena MCP Integration (Optional)

Configure [Serena](https://github.com/oraios/serena) MCP to enable enhanced functionality through semantic code
analysis.

### What is Serena?

Serena is a semantic code analysis tool based on LSP (Language Server Protocol) that supports 30+ programming languages.
It enables symbol-level code search and analysis.

### Configuration

Add the following to your project's `.mcp.json`:

```json
{
  "mcpServers": {
    "serena": {
      "type": "stdio",
      "command": "uvx",
      "args": [
        "--from",
        "git+https://github.com/oraios/serena",
        "serena",
        "start-mcp-server",
        "--context",
        "ide-assistant",
        "--project",
        ".",
        "--enable-web-dashboard",
        "false"
      ]
    }
  }
}
```

### Enhanced Features

| Skill             | Enhancement with Serena                                                                       |
|:------------------|:----------------------------------------------------------------------------------------------|
| `/generate-spec`  | References existing code API/type definitions for consistent specification generation         |
| `/check-spec`     | Provides high-precision API implementation and signature verification via symbol-based search |
| `/task-breakdown` | Analyzes change impact scope for accurate task dependency mapping                             |

### Without Serena

All features work without Serena. Text-based search (Grep/Glob) is used for analysis and works language-agnostically.

### Recommended Directory Structure

Both flat and hierarchical structures are supported.

#### Flat Structure (for small to medium projects)

```
.sdd/
├── CONSTITUTION.md               # Project constitution (highest level)
├── PRD_TEMPLATE.md               # PRD template (optional)
├── SPECIFICATION_TEMPLATE.md     # Abstract specification template (optional)
├── DESIGN_DOC_TEMPLATE.md        # Technical design document template (optional)
├── ADR_TEMPLATE.md               # Decision log (ADR) template (optional)
├── requirement/                  # PRD (Requirements Specification)
│   └── {feature-name}.md
├── specification/                # Persistent knowledge assets
│   └── {feature-name}_spec.md    # Abstract specification
├── adr/                          # Persistent decision log
│   └── {feature-name}.md         # Decisions and rationale (append-only)
└── task/                         # Temporary task logs (deleted after implementation)
    └── {ticket-number}/
        └── design-draft.md       # Technical design draft, deleted after implementation
```

#### Hierarchical Structure (for medium to large projects)

```
.sdd/
├── CONSTITUTION.md               # Project constitution (highest level)
├── PRD_TEMPLATE.md               # PRD template (optional)
├── SPECIFICATION_TEMPLATE.md     # Abstract specification template (optional)
├── DESIGN_DOC_TEMPLATE.md        # Technical design document template (optional)
├── ADR_TEMPLATE.md               # Decision log (ADR) template (optional)
├── requirement/                  # PRD (Requirements Specification)
│   ├── {feature-name}.md         # Top-level feature (backward compatible with flat structure)
│   └── {parent-feature}/         # Parent feature directory
│       ├── index.md              # Parent feature overview and requirements list
│       └── {child-feature}.md    # Child feature requirements
├── specification/                # Persistent knowledge assets
│   ├── {feature-name}_spec.md    # Top-level feature (backward compatible with flat structure)
│   └── {parent-feature}/         # Parent feature directory
│       ├── index_spec.md         # Parent feature abstract specification
│       └── {child-feature}_spec.md   # Child feature abstract specification
├── adr/                          # Persistent decision log
│   ├── {feature-name}.md         # Top-level feature (backward compatible with flat structure)
│   └── {parent-feature}/         # Parent feature directory
│       ├── index.md              # Parent feature decision log
│       └── {child-feature}.md    # Child feature decision log
└── task/                         # Temporary task logs (deleted after implementation)
    └── {ticket-number}/
        └── design-draft.md       # Technical design draft, deleted after implementation
```

#### Document Dependencies

```
CONSTITUTION.md → requirement/ → *_spec.md → task/{ticket-number}/design-draft.md → Implementation
```

`adr/{feature-name}.md` persists the decisions, rationale, and rejected alternatives extracted
from `design-draft.md` before it is deleted (append-only; see [Migration from v4.x](#migration-from-v4x)
if you have existing persisted `*_design.md` files to convert).

All documents are created following `CONSTITUTION.md` project principles.

**Hierarchical structure usage examples**:

```
/generate-prd auth/user-login   # Generate user-login PRD under auth domain
/generate-spec auth/user-login  # Generate specification under auth domain
/check-spec auth                # Check consistency for entire auth domain
```

### Project Configuration File

Place a `.sdd-config.json` file in your project root to customize directory names and language.

```json
{
  "root": ".sdd",
  "lang": "en",
  "directories": {
    "requirement": "requirement",
    "specification": "specification",
    "adr": "adr",
    "task": "task"
  },
  "index": true,
  "naming": {
    "ignore_patterns": ["*_test.md"]
  }
}
```

| Setting                     | Default         | Description                                                                                       |
|:----------------------------|:----------------|:--------------------------------------------------------------------------------------------------|
| `root`                      | `.sdd`          | Root directory                                                                                    |
| `lang`                      | `en`            | Language (`en` or `ja`)                                                                           |
| `directories.requirement`   | `requirement`   | PRD (Requirements Specification) directory                                                        |
| `directories.specification` | `specification` | Specification/design document directory                                                           |
| `directories.adr`           | `adr`           | Architecture Decision Record (decision log) directory                                             |
| `directories.task`          | `task`          | Temporary task logs directory                                                                     |
| `index`                     | `true`          | Boolean. Build a compressed `.sdd` document index (SQLite → `index.md`) at session start for token reduction. Set to `false` to disable. |
| `naming.ignore_patterns`    | `[]`            | Glob patterns (`fnmatch` syntax) matched against a file's basename. Matching files skip the `requirement`/`specification` naming check (e.g. `*_test.md` for test fixtures). |

**Notes**:

- If the configuration file doesn't exist, default values are used
- Partial configuration is supported (unspecified items use defaults)
