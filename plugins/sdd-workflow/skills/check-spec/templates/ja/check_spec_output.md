## 仕様書・実装整合性チェック結果

### 対象ドキュメント

- 仕様書（比較の第一級基準）: `${SDD_SPECIFICATION_PATH}/[{親機能名}/]{機能名}[_spec].md`
- 設計ドラフト（存在時のみの補助入力）: `${SDD_TASK_PATH}/{チケット番号}/design-draft.md`
  （選定根拠: `{design_draft_scope}`）

※ 階層構造の場合、親機能は `index.md` または `index_spec.md`
※ 設計ドラフトが存在しない場合は該当行を省略する。実装完了後は不在が通常状態であり、指摘対象ではない
※ `design_draft_scope` が `unscoped` の場合は、設計ドラフトが {n} 件見つかったがどれも今回の対象に紐付けられなかった旨を
記載し、該当ファイルを列挙して `--ticket <番号>`（`--ticket=<番号>` も可）での再実行を推奨する

#### 降格サマリー（常に出力する）

`impl-status` により「仕様に記載があるが実装が無い」の判定は Critical から降格する。v4.x では無条件 Critical
だったため、v4 世代の文書は `impl-status` を持たず全件が降格対象になる。件数を必ず明示する:

| 降格                                              | 件数    | 対象 spec        |
|:------------------------------------------------|:------|:---------------|
| Critical → 🟡 Warning（`impl-status` 未設定）         | {n} 件 | `{spec_paths}` |
| Critical → 🔵 Info（`not-implemented`/`in-progress`） | {n} 件 | `{spec_paths}` |

※ この {合計} 件は**解決済みではない**。判定不能または意図した先行であり、上の Critical 件数には含まれない。
降格が 0 件の場合も 0 を明記して出力する

### 未実装機能

仕様書に記載されているが、実装が確認できなかった機能。判定は spec の `impl-status` に応じて分岐する：

- `impl-status: "implemented"` → **🔴 Critical（退行）**: 実装済みと宣言されているのに実装が見つからない
- `impl-status: "not-implemented"` / `"in-progress"` → **🔵 Info（意図した先行）**: 仕様が実装に先行している正常な状態
- `impl-status` 未設定 → **🟡 Warning（判定不能）**: `impl-status` の追加を推奨。
  `/recommend-front-matter` は未設定の spec を**列挙するだけ**で値は書き込まないため、列挙された spec ごとに
  実装の実態を確認し、`implemented` / `in-progress` / `not-implemented` のどれに当たるかを自分で記入する

| 機能    | 仕様書の記載箇所          | spec の `impl-status` | 判定             |
|:------|:-------------------|:---------------------|:---------------|
| {機能名} | spec の {セクション}（{要求ID}） | `implemented`         | 🔴 Critical（退行） |
| {機能名} | spec の {セクション}（{要求ID}） | `not-implemented`     | 🔵 Info（意図した先行） |
| {機能名} | spec の {セクション}（{要求ID}） | 未設定                  | 🟡 Warning（判定不能） |

### 推奨アクション

#### 優先順位

1. **Critical の差異を優先的に解消**
    - 公開 API の不一致（引数、戻り値の型、CLI オプション、環境変数）
    - 仕様書に記載された機能の未実装（spec の `impl-status` が `implemented` の場合 = 退行）
    - データモデルの不一致

2. **Warning の対応**
    - 仕様書に記載された機能の未実装（spec に `impl-status` が未設定の場合 = 判定不能。
      実装の実態を確認したうえで `impl-status` を手動で記入する）
    - 仕様書の制約を超えた実装の是正
    - 仕様書に未記載の実装の文書化
    - モジュール構成の整合性確保（設計ドラフトを読み込んだ場合のみ）

3. **Info の確認**
    - 仕様書に記載された機能の未実装（spec の `impl-status` が `not-implemented`/`in-progress` の場合 = 意図した先行。対応不要）
    - 技術スタックの軽微な差異
    - ドキュメント改善の検討

4. **ドキュメント間整合性の確認**（`--full` オプション実行時）
    - spec-reviewer が検出したドキュメント間の不整合を確認
    - PRD ↔ spec ↔ adr の整合性を確保

5. **adr ↔ 実装の手動確認**（自動検出されないため）
    - `${SDD_ADR_PATH}/{機能名}.md` の直近エントリを読み、実装が今もその決定に従っているか確認する
    - 従っていない場合は旧エントリを書き換えず、`Supersedes` 項目を持つ**新しいエントリを追記**する
      （`adr/` は append-only）

#### 対応フロー

1. spec ↔ 実装の不整合を確認し、差異の原因を特定
2. 仕様書または実装のどちらを修正するか判断:
    - 実装が正しい場合 → 仕様書を更新
    - 仕様書が正しい場合 → 実装を修正
3. `--full` オプション実行時は、spec-reviewer の指摘も確認:
    - PRD ↔ spec の不整合
    - spec ↔ adr の不整合
    - CONSTITUTION.md 違反
4. 修正後、再度 `/check-spec` を実行して確認
